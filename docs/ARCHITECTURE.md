# CHIGIRI Beauty Architecture

## Request flow

1. ブラウザが相談文、現在の担当者、直近履歴、構造化メモリを`/api/chat`へ送信する。
2. API境界で入力長、担当者、履歴件数、画像の所有権を検証する。
3. 会話エンジンが確認済み条件、質問済み項目、提案段階、安全上の停止条件を決定する。
4. 初期聞き取りと安全停止は固定ルールで返す。
5. 色提案が必要なメイク相談では、パーソナルカラーを本人へ確認する。未診断の場合は写真から推測せず、希望する印象と利用場面を使う。
6. 提案段階ではOrcaRouterへ必要最小限の文脈、公式確認済み候補、取得できた口コミの出典・平均評価・件数だけを渡す。口コミ本文や傾向は生成しない。
7. OrcaRouterが未設定・失敗・空応答の場合はローカル応答へフォールバックする。
8. 相談履歴はD1へ、所有者がアップロードした画像はR2へ保存する。

## Trust boundaries

| Boundary | Control |
| --- | --- |
| Browser → API | 種別・長さ・件数・許可値を検証 |
| Image ID → R2 | 現在の利用者が所有する画像だけを取得 |
| App → LLM | 秘密キーはサーバー環境変数、公式商品候補だけを渡す |
| LLM → User | 医療診断・効果保証・未確認商品情報を禁止 |
| App → D1 | 利用者スコープで相談履歴を保存 |

## Cost and availability

| Design | Cost | Availability | Operational load |
| --- | --- | --- | --- |
| 全ターンLLM | 高い | LLM障害の影響大 | 低い |
| 全ルールベース | 低い | 高い | 会話品質の保守が重い |
| CHIGIRIのハイブリッド | 初期聞き取り分を削減 | LLM障害時も継続 | ルールとプロンプトの両方を管理 |

採用構成は、危険判定と状態遷移を決定的なロジックに残し、自然な自由文生成だけをLLMへ任せます。
